# Shielded ZVM ownership plan

**Current environment, October 11, 2026:** chain-backed validation is limited to `devnet.zenon.foo` and ZVM devnet. Follow the [devnet validation plan](SHIELDED-DEVNET-VALIDATION.md). Production/mainnet acceptance remains future work; no production ZVM availability is assumed. Offline tests remain local. The user authorized six isolated devnet contracts and their disposable mint/claim/recovery experiment under a 1 devnet ZNN fee cap; that lifecycle now passes. Hosted app activation and broader release acceptance are separate.

Accepted direction · October 10, 2026 · implementation baseline: merged [PR #30](https://github.com/0x3639/zft/pull/30), `d91d15d909873614de607ce18a164d8c96484022`.

The next ZFT milestone is user-held, shielded ownership enforced by a ZVM contract. The client holds the spending secrets and generates proofs; the contract verifies authorized transitions and prevents a note from being spent twice. Cloudflare hosts the application and replaceable support services. A central PS mint, issuer signing key, or service-maintained ownership database is not part of this target.

This direction supersedes the hosted PS release sequence and the proposal v0.2 sequence that puts a new public ERC-721 launch ahead of shielded ownership. The existing public ZFT v1 contract, assets, files, routes and recovery paths remain supported. This plan approves the engineering direction; the experimental protocol and Groth16 choice are implemented locally, while independent qualification and deployment acceptance remain unfinished. The [implementation roadmap](IMPLEMENTATION.md) tracks SH0–SH7 separately from historical C0–C6 work.

The [implementation plan](SHIELDED-ZVM-IMPLEMENTATION.md) breaks SH1–SH6 into concrete tasks, repository boundaries and the first two-client lifecycle milestone. It also specifies the required image-to-metadata binding to freeze during SH1.

## Decisions and scope

| Decision                               | Planned behavior                                                                                                                                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Ownership and double-spend enforcement | ZVM contract state and a reviewed proof verifier are authoritative. Each valid transfer consumes one existing note and creates exactly one successor for the same asset.                                                       |
| User custody                           | Spending and recovery secrets are generated and retained on the user's device or in user-controlled recovery files. Servers receive public data, proofs or optional ciphertext they cannot decrypt.                            |
| Hosting                                | Cloudflare remains the selected application host. An index, optional ciphertext backup and optional gas sponsor may improve usability; each must have a documented replacement or bypass.                                      |
| Reference experience                   | Keep the picture-file mint, send, claim, cancel and recover experience where compatible with the new protocol. This is a new cryptographic construction, not PS interoperability or an import of Nonfungible.cash credentials. |
| Existing public assets                 | Preserve the deployed ERC-721 and all v1 semantics. A separately versioned shielded deployment and file format must identify their protocol and deployment explicitly.                                                         |
| Display and identity                   | Use ZFT-managed shielded inventory. MetaMask can provide optional public profile identity or gas payment without holding note secrets. Ordinary wallet NFT inventory and a display Snap are separate later decisions.          |
| Initial exclusions                     | Legacy NFC/PS asset import, v1 migration or wrapping, marketplace/sale settlement, Snap, apex promotion and mainnet launch. No automatic conversion of existing assets.                                                        |

The owner secret in the PS reference and the mint's signing secrets serve different roles. Prior issuer key-custody experiments did not centralize users' wallet keys. The architectural change here removes the mint's authority and availability requirement from the new ownership path, rather than relocating that issuer key to Cloudflare or a contract.

## Authority and availability

| Component                          | Responsibility                                                                                                                   | Required failure behavior                                                                                                                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User client and recovery files     | Own secrets, validate assets, prepare destination authority, generate proofs and recover pending operations                      | A fresh client can recover using user-held data without an account reset or service-held decryption key.                                                                                 |
| ZVM contract                       | Verify public inputs and proofs, enforce asset creation rules, consume nullifiers and append valid output commitments atomically | Invalid proofs and duplicate spends leave ownership state unchanged. No operator may mint successors, seize notes or bypass verification.                                                |
| ZVM execution and underlying chain | Establish transaction ordering, state derivation, finality and public data availability                                          | The qualification must demonstrate independent verification and an alternative submission path; multiple URLs alone do not establish independence.                                       |
| Cloudflare frontend and index      | Distribute public client artifacts and derived views                                                                             | A pinned, reproducible client can be self-hosted, and public state can be rebuilt without Cloudflare's database.                                                                         |
| Optional backup and sponsor        | Store user-encrypted records or submit already-authorized transactions/pay gas                                                   | Losing either service cannot reveal spending keys or prevent a user with recovery data and a viable fee/submission path from proceeding. A sponsor's gas key has no ownership authority. |

The disappearance drill must remove the ZFT frontend, index, backup endpoint and sponsor together. A second client must reconstruct witnesses from available public chain data, recover a pending operation and submit a transfer through an independently operated path. Passing requires the chain itself to remain live and its data available. This plan does not promise continued transfers after the underlying chain stops.

A malicious hosted frontend can steal secrets while a user is using it. Publish reproducible client, circuit and verifier artifacts with integrity pins and a self-hosting procedure; document the remaining browser and software-supply-chain trust. Encryption at rest does not remove that risk.

## Protocol work required before implementation freezes

SH1 must specify complete algorithms and schemas, rather than treating a commitment formula or a choice of proof library as a protocol. Select the proof system, circuit hash functions, field encodings, setup assumptions, verifier, versioning and license/build requirements with evidence from SH2.

1. **Creation and provenance.** Define permissionless creation, asset identity, uniqueness policy and creator authorization. Bind every protected metadata/content field, recipient, nonce and expiry to the same authorized operation. If commit/reveal is retained, the commitment and reveal authorization must cover the same fields and intended minter; a public reveal must not let another signer substitute provenance. Hash uniqueness establishes byte identity, not copyright or original authorship.
2. **Notes and nullifiers.** Bind the asset and spending/nullifier authority into the note commitment. Derive the spend nullifier deterministically from authority constrained by the proof and the correct protocol/deployment domain. The prover must not be able to choose a fresh unrelated nullifier key for each spend. Specify canonical encodings, range checks and unambiguous handling of full asset digests across fields; reducing a digest modulo a field is not an injective encoding.
3. **Transfer relation.** Prove membership of an existing note, knowledge of its spending authority, correct nullifier derivation, and conservation into exactly one valid successor of the same asset. Bind the intended output and all public inputs to the proof. Specify permitted anchor roots and atomic contract updates. Accepting an older membership root must never bypass the current spent-nullifier check. Reject malformed points, out-of-range inputs, wrong assets, wrong chains and wrong deployments.
4. **One ownership authority.** The new contract must not maintain an ERC-721 owner field alongside an unrelated shielded owner field. Existing v1 continues to use its own canonical ERC-721 state. Any later bridge needs a separate reviewed conservation and failure model.
5. **Public showing and privacy.** Specify separately what a showing proves about a historical note and what establishes unspentness at an identified chain state. Membership in an old root alone is not current ownership. Decide how selective public showing affects asset, holder and nullifier linkability before adding profile integration. A public showing may disclose a selected association without requiring every intermediate holding to be public.
6. **Front-running, retries and finality.** A copied transaction or proof must not redirect the successor or modify protected provenance. Define fees and any relayer binding explicitly. Preserve the same destination and exact pending operation across retries. Define reorg, expiry, replaced transaction and ambiguous-submission behavior against the selected chain's actual finality model.
7. **Witness and recovery data.** Specify the public event/state data needed for inclusion proofs, root updates and independent reconstruction, including pagination, gaps and reorgs. Specify the user-held material needed to rediscover notes and recover pending outputs. An unavailable index cannot silently become the sole holder of required witness data.

The privacy model must enumerate public mint data, asset identifiers, commitments, nullifiers, transaction senders, fees, timing, network metadata and deliberate profile disclosures. Choose and justify the anonymity set. Do not claim that rerandomized proofs erase a deterministic public identifier, or that a public showing makes all transfer privacy pointless.

Proof-system selection must explicitly distinguish per-circuit setup, universal setup and transparent setup. A universal ceremony is still a setup assumption. Select only after measuring verifier compatibility/cost, prover time and memory on target browsers and phones, artifact size, reproducibility and independent review coverage. No concrete proof system is approved by this plan.

## File and browser lifecycle

The shielded format uses a new protocol/version discriminator and pinned deployment parameters. It must reject incompatible v1 and PS records instead of reinterpreting them. Public artwork, social previews and proof downloads contain no spending or recovery authority.

Before broadcasting a claim, cancel or transfer, the client must generate the successor secret, persist the exact operation and require a saved, verified recovery copy containing everything needed after a lost response. Test recovery from a fresh client at each boundary. A browser crash after successful submission must not leave the asset controlled by an unsaved key. Recovery must resolve the existing operation before creating a different successor.

Possession of a copied bearer file permits competing claims until one is finalized under the protocol's rules. Sending the file alone is not settlement. The interface must distinguish prepared, submitted, uncertain, finalized, historical, spent and unavailable states; RPC errors are not evidence that a transfer succeeded or an asset is unspent. Keep old recovery information until confirmation and reorg handling permit cleanup.

Reuse the prior lab's strict parsing, version separation, recovery-before-submit and failure-injection methods. Do not treat its PS equations, browser modules or issuer test totals as a verified implementation of this new system.

## Required adversarial coverage

- Two competing spends of the same note: at most one succeeds, including when they use different admissible anchor roots; failed operations leave no partial output or nullifier update.
- Wrong asset, changed nullifier authority, substituted successor, altered provenance/content, field aliases, malformed proof/point, wrong deployment and replayed authorization: reject without state changes.
- All transfer entry points and internal hooks: one conservation and authorization policy; no unchecked standard-token path or administrative bypass.
- Crashes before/after recovery persistence, proof creation, broadcast, receipt and finality; lost responses and third-client recovery use the saved successor and original operation.
- Reorgs, stale roots, stale or lying indexes/RPCs, missing event ranges, index rebuild and total Cloudflare service loss; display historical or unavailable evidence honestly.
- Bearer-file copies, invalid/encrypted-file imports and public-proof export; no secrets in HTTP, analytics, exceptions, URLs, public pages or OG artifacts.
- Real device proving, memory, storage, download/reselection and recovery; public showing and gas/profile correlation measured against the privacy claims.

Use deliberate verifier/circuit/state-machine mutations to prove the relevant tests detect weakened constraints. Test passing, bot review and same-author implementations do not replace independent cryptographic review.

## Publication and evidence policy

Continue local work in one consolidated engineering branch with unsigned unpublished checkpoints when useful. Preserve an unsigned backup, batch-sign the final publishable history, verify the expected signer and tree, and submit one consolidated PR for review. Sign follow-up published fixes without rewriting shared history. Do not reopen the series of small per-adapter PRs. Merge and deployment remain user actions requiring explicit authorization.

All prior PS validation manifests and the signed PR #30 handoff remain historical evidence for their pinned revisions. Planning edits do not refresh their source hashes or make their results cover SH1–SH7. The existing `ps:release-check` script and pending PS evidence template apply to the former issuer candidate; they do not authorize or assess this shielded design. The separate `research/shielded-validation.json` now records the local candidate and open release gates.

C1/C4 and PS-OWN-01 remain unresolved historical PS review items. They are not silently closed by this architectural decision, and their test/review status does not transfer to the new proof system. Managed issuer keys, PS signing backends and issuer hosting are removed from the active release path. Independent shielded review, browser/device acceptance, chain feasibility and explicit staging approval remain required.

## Follow-up decisions

SH1/SH2 must resolve the note schema, creation/provenance rules, public-versus-private asset identifiers, showing/freshness protocol, proof system/setup, chain limits and finality, fee/submission alternatives and reproducible witness availability. Later acceptance needs an independent reviewer and real devices. Cloudflare has been selected as the application host; this does not authorize paid resources, a deployment or server access to user secrets.

The supplied `NFC_ZVM_Proposal_v0.2.md` remains a reviewed input. Its mint commitment/reveal binding, ERC-721 state integration, sale authorization/reentrancy, recovery ordering, legacy import, nullifier binding, RPC trust and privacy conclusions require revision or exclusion as described above. Legacy imports and sales are excluded from this milestone rather than carried forward as unfinished launch requirements.
