# Local PS browser credential client

This C5 research increment follows merged PR #21 (`2a2bc71`). The console's **Browser client** link opens an isolated client whose dedicated module Worker generates owner secrets, issuance/transfer proofs and encrypted pending journals. The existing local issuer still runs in Node. The deployed app, v1 custody and local PS cryptographic transcripts are unchanged. **Public fixture issuer keys: do not use real assets.** [Current evidence](../research/ps-browser-client-validation.json) records the exact scope; [PS-OWN-01](PS-REVIEW-PACKET.md#open-review-item-former-holder-and-cross-asset-forgery) remains open for independent review.

## Run and use

```sh
pnpm --dir research/ps-lab --ignore-workspace install --frozen-lockfile --ignore-scripts
pnpm --dir research/ps-lab --ignore-workspace browser:local
```

Open the printed launch link and follow **Browser client**. Alice, Bob and Restored are separate encrypted browser slots for one test operator, not authenticated users.

1. Create a browser copy with a public test password, or open the existing copy for that role. Creation refuses an existing slot. The password must contain 12–1024 UTF-8 bytes and valid Unicode.
2. Prepare a mint using a normalized test artwork. A fresh secret and proof are generated in the Worker, and the encrypted pending journal must commit before preparation succeeds.
3. Enter a file password and create an encrypted recovery download. Use the Save link, then reselect that actual file, re-enter its password and choose **Verify reselected recovery file**. The Worker checks the exact ciphertext hash, decrypts with the remembered file ID and compares the complete recovery snapshot; acknowledgment must also commit before submission.
4. Submit the saved request. A test checkbox discards the returned response after the issuer has committed. **Recover issuer response** retrieves the exact result; it does not mint a replacement request. Unknown recovery or invalid responses preserve pending material. An expired, uncommitted request remains pending and cannot be submitted; this lab has no renewal or abandonment UI.
5. To transfer, export an encrypted bearer file and communicate its expected file ID separately. Bob selects that file, supplies the ID/password and prepares a claim, then follows the same recovery/save/submit sequence. Cancellation swaps the holder's credential to a new secret under the same gate. Merely handing over a copied file is not a completed transfer.
6. To recover into Restored, create its browser copy and import the saved recovery file with its separately retained ID/password. Recover the original issuer response, then verify and save the credential. Replaying an old recovery cannot clear a locally remembered spent flag.

The three roles share the running lab's issuer and launch capability; this is not multiuser isolation. The Node console can also interact with that issuer. Stopping the process destroys its registry; old downloads or IndexedDB rows do not make a newly started issuer accept old credentials. Locking or reloading never extends the issuer's five-minute session. Reload requires the original launch link again, then reopening the same role.

## Browser and issuer boundary

[BrowserClient](../research/ps-lab/web/client.mjs) uses the existing generated [local profile](PS-LOCAL-ENGINE.md), snapshot validator and [browser vault](PS-BROWSER-VAULT.md). It creates mint/claim/cancel proofs, validates replacements, and retains pending and completed recovery records. Only the [Worker](../research/ps-lab/web/client-worker.mjs) holds decrypted working state. The page receives identifiers, local flags and explicitly requested encrypted exports. It never receives plaintext credential exports or snapshots. Password entry necessarily exists briefly in the page before reaching the Worker; fields clear after actions. The journal password remains in Worker memory while unlocked.

The new `/issuer` POST route accepts only exact `bootstrap`, `session`, `submit` and `recover` schemas. Bootstrap provides the complete caller-pinned manifest, random local client IDs and three public normalized fixture images. Submission sends the protocol wire and response-retrieval capability; recovery sends its digest and capability. No browser owner secret, blinding scalar, bearer envelope, recovery snapshot or vault password is sent to Node by this flow. Node returns public sessions and protocol responses. Tests verify that its separate plaintext client databases remain empty for these operations; the original Node console still uses those stores when invoked.

The route shares the console's exact Host/Origin/launch-capability checks, no-CORS policy, strict UTF-8/canonical JSON, fixed assets, CSP and generic errors. Its body limit is 16,384 bytes, protocol requests remain 12,288 bytes, and new operations stop at 24 issuer commits while exact recovery remains available. Existing session, connection and reader bounds remain. The capability stays in page/Worker memory for requests and is removed from the address fragment. This is a trusted, loopback, single-operator development surface. It is not a hosted API, browser-origin identity scheme or production resource/DoS qualification.

## Encrypted journal and recovery

The separately versioned `zft-ps-browser-client-state-v1` journal does not change existing `zft-ps-local-vault-v1` transfer/recovery files. Its exact outer fields are `format`, `kdf`, `cipher`, `client_id`, `manifest`, `salt`, `iv`, `ciphertext`, `tag`. It uses the same fixed scrypt N=32768/r=8/p=1, 16-byte random salt, AES-256-GCM, 12-byte random IV and 16-byte tag. Canonical header bytes are authenticated as AAD. Every save freshly encrypts the whole journal; plaintext is limited to 1,048,576 bytes and the outer wire to 2,101,248 bytes. Header and decrypted manifest/client identity both match the caller's pins.

The encrypted content has exact fields `format`, `client_id`, `manifest`, `operations`, `credentials`. At most eight operations and eight credentials are retained. An operation includes its validated snapshot, expected backup ID/hash, acknowledgment and exact response. Credentials include a validated bearer wire and a local spent flag. Completed operations must reproduce the recorded credential and retain known source-spent state. Historical entries are not pruned; the small cap deliberately stops further work instead of silently deleting recovery material.

[IndexedDB](../research/ps-lab/web/client-storage.mjs) uses separate database `zft-ps-browser-client-lab-v1` with at most eight `{key, revision, wire}` rows. A single readwrite transaction checks expected revision, slot capacity and the new encrypted wire. The client publishes its new in-memory state only after transaction completion. Failed preparation cannot release a submit-ready request; failed acceptance leaves the previous pending ciphertext recoverable. Stale writers cannot overwrite a later revision. Workers serialize actions; `BrowserClient` is an internal serialized-operation component, not a concurrent public API.

Lock terminates the Worker and clears page passwords, file selection and download links. Epoch checks reject asynchronous completion after lock. If storage already committed, that ciphertext may remain but the old Worker result cannot reopen the client. Explicit, hidden/pagehide and five-minute idle locking remain lifecycle protections, not secure memory erasure. Browser storage rollback, eviction, quota errors, arbitrary filesystem faults, cross-device synchronization and power loss are unqualified. A valid old recovery in a fresh client may expose a credential already spent at the issuer; only the issuer's registry determines spendability. Existing files/passwords are not revoked by later saves.

## Validation and acceptance

[Evidence](../research/ps-browser-client-validation.json) records **201 local tests**, including 21 new browser-client tests, and **51 mutation controls**, six new. The existing 21 actual SIGKILL locations are unchanged. New tests cover encrypted mint/claim/cancel, exact recovery reselection, failed preparation/acknowledgment/acceptance persistence, stale writers, lock during encryption/commit, replay after spend, unknown recovery, malformed responses, file/password/pin substitution, authenticated malformed journal contents, caps and secret-free summaries. Worker-thread tests exercise real HTTP with an in-memory persistence adapter; they do not substitute for actual IndexedDB tests.

Review identified a missing inner manifest/client-ID pin check during development; an authenticated-journal regression now covers it. Both outer and decrypted identities now match the caller; a temporary mutation removing this check must fail the final regression. Other controls remove the backup gate, publish memory before commit, revive spent state, reopen after lock or leak snapshots. The fixed ESM scanner was also narrowed to exclude whitespace in specifiers after the UI's `import` form label was mistaken for an import by the closure test; no crypto source or dependency changed.

Codex's in-app desktop browser generated a fresh pending mint, downloaded the actual Worker-encrypted recovery file, reselected it and transitioned from unacknowledged to ready. Submission deliberately lost its response; a separately created Restored client imported the saved file and recovered one credential. Seven real IndexedDB checks passed (commit, encrypted row shape, stale revision, abort after put, two-connection race, wrong pin and cap). The cap test uses synthetic schema-valid ciphertext; authentication is tested separately. The download-event API timed out, but the browser-created file was present in Downloads and actual reselection authenticated it. Batched automation of the file chooser stalled on two attempts; separate picker steps succeeded. Those delays also exercised locking and uncommitted-session expiry, without extending timeouts.

Full browser claim/cancel UI paths, ordinary browsers, phones and multi-device acceptance remain open; automated client/Worker/HTTP tests cover those underlying protocol operations. Desktop and 390px layout checks, password clearing, observed console logs and lock/reopen are recorded in the evidence. Existing reference/app checks are inherited from PR #21 CI, not newly run locally in this slice; PR CI reruns them. Ten earlier manifests remain frozen historical evidence.

This is a local browser credential workflow, not the ZFT product integration. Browser PNG import/export and custom artwork normalization, collection/artwork display, wallet identity/endorsement, public showing/state UI, device qualification and production trust/key/retention policy remain. No Snap, wrapper, app migration, issuer deployment or apex promotion. Same-author protocol composition and unqualified secret BigInt side channels remain research limitations. C1/C3 are partial, C4 including PS-OWN-01 is pending, C5 remains partial and C6 is unimplemented.
