# Local PS browser vault

This C5 increment follows merged PR #20 (`b859b3e`). It moves **opening, validating and re-encrypting existing vault files** into a dedicated browser worker and stores only encrypted envelopes in IndexedDB. Mint/claim/cancel, recovery submission and the issuer still use the [disposable Node console](PS-BROWSER-LAB.md) and its plaintext SQLite stores. This is not a complete browser-owned PS client, a hosted wallet or encrypted Node working storage.

## Try it locally

Start `pnpm --dir research/ps-lab --ignore-workspace browser:local` and open the printed launch link. Prepare an encrypted recovery or credential export in the console, then follow **Browser vault**. Use public test passwords and files only.

1. Select the expected backup identity supplied by the running console. Select its encrypted JSON file and enter its password. The worker authenticates the envelope and validates each bearer/recovery record against the complete pinned manifest.
2. Enter a password for the new copy and choose **Encrypt and save in browser**. Fresh encryption must finish before one IndexedDB transaction saves the ciphertext and advances its revision. The password fields clear after each attempted operation.
3. Prepare the download, use its explicit Save link and reselect the saved file to compare exact bytes. This comparison does not acknowledge an issuer operation or prove disk durability. Preserve the previous export until the new one is saved and verified.
4. Lock the vault, then use **Open browser copy** with the new password. The page also locks on visibility loss, page exit and five minutes without interaction. Refresh needs the complete launch link again; the random port and temporary issuer are not a stable account system.

The console can create both recovery and bearer exports. The new page only opens/reprotects existing records; it does not construct issuance/claim proofs, normalize artwork, show artwork, create a new UI vault, submit recovery or authenticate a wallet. A re-encrypted recovery file is not automatically registered as a new backup in the Node console. Its selected-file check is separate from the console's issuer acknowledgment gate.

## Cryptography and trust boundary

The bytes remain [zft-ps-local-vault-v1](PS-LOCAL-VAULT.md): scrypt N=32768/r=8/p=1, 32-byte output, fresh 16-byte salt; AES-256-GCM with a fresh 12-byte IV and 16-byte tag. The complete canonical header is additional authenticated data. Passwords use the same well-formed Unicode and 12–1024 UTF-8 byte policy. No KDF parameters come from the file. Existing file/content/record limits remain unchanged.

[BrowserVault](../research/ps-lab/web/vault.mjs) uses already lock-pinned noble-hashes 2.4.0 `scryptAsync` and browser [WebCrypto AES-GCM](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt), with a nonextractable imported key. The [fixed module builder](../research/ps-lab/web/modules.mjs) adapts the unchanged reference/local validators: Node assert/Buffer/hash/random adapters become small browser helpers; the unchanged recovery validator and vault schema are extracted without store methods. Exact replacement anchors fail closed if their sources change. It serves only a fixed dependency closure, not request-selected filesystem paths. The existing noble MIT notices are served alongside it. No new dependency, lockfile, upstream website bundle or cryptographic transcript is introduced.

The full manifest and expected vault ID come from authenticated local-console status, never from the uploaded file. This is a development trust bootstrap from the same local operator/process, not independent trust distribution. Status contains public key material but no credential/recovery secret. The vault page makes one authenticated status request, then drops its launch token. Its passwords and decrypted records are not sent to Node; worker messages return record kind/identifier pairs and explicit encrypted exports. The older console still sends its own passwords/files to Node.

The worker accepts one operation at a time. Epoch checks prevent an asynchronous open/seal from returning after lock. The UI terminates its worker on lock, clears selected files/passwords/download URLs and rejects pending responses. Byte buffers are cleared where possible, but strings, structured-clone copies, garbage collection and cryptographic runtime memory are not securely erased. Workers provide lifecycle separation, not protection against malicious same-origin scripts, browser extensions or a compromised browser/server. Secret BigInt arithmetic remains unqualified for production side channels. Randomness/device qualification and independent composition review remain open.

## Browser storage contract

[IndexedDB storage](../research/ps-lab/web/storage.mjs) uses database `zft-ps-browser-vault-lab-v1`, store `vaults`, and keys formed from the hash of the pinned manifest plus vault ID. At most eight entries contain `{key, revision, wire}`. Only the canonical encrypted outer envelope is persisted; its manifest, identity, lengths and revision remain visible. The storage layer checks schema and pins; the worker authenticates ciphertext on opening.

A readwrite transaction compares the caller's expected revision, enforces the slot limit and saves the incremented revision with exact ciphertext. Success resolves only on transaction completion, not request success. Aborts leave the previous entry intact. Two database connections cannot both overwrite the same expected revision. The UI refuses to import a different file over an existing browser copy; reopen that copy first. There is no cross-tab lock broadcast: each tab must lock separately. A transaction that already committed when lock occurs can leave its encrypted copy saved, while generation checks prevent the old result from reopening the page.

This is compare-and-swap conflict handling, not anti-rollback. A valid older export can still decrypt. Restoring old IndexedDB data, origin eviction/clearing, quota exhaustion, browser termination, power loss, arbitrary I/O, malicious rollback, multi-device synchronization and retention/availability are not qualified. A transaction's completion is not a device durability guarantee; see [IndexedDB transaction behavior](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction). Changing the password does not revoke old copies. Ending the Node lab still destroys its registry and prevents continuing its operations, even if browser ciphertext remains.

## Validation and acceptance

[Current evidence](../research/ps-browser-vault-validation.json) records 180 local tests (20 new), 45 deliberate mutation controls (five new) and 21 unchanged SIGKILL locations. New tests execute the generated browser modules under Node WebCrypto and worker-thread adapters: fixed-cost scrypt parity, both directions of file compatibility, pins, modified ciphertext/tag/salt/IV/AAD, authenticated invalid records/UTF-8/JSON, fixed KDF/header bounds, Unicode password policy, locking and asynchronous worker cancellation. These are portable-module/backend checks, not 20 real-browser tests or independent cryptographic review. List comparisons ignore in-memory insertion order because sealed canonical JSON orders record keys.

In the actual Codex in-app desktop browser, an API-generated test recovery file was opened and validated in the worker, re-encrypted, committed to IndexedDB, locked and reopened. Seven explicit [real IndexedDB checks](../research/ps-lab/web/checks.mjs) cover successful commit, ciphertext-only row shape, stale revision, abort after put, competing database connections, wrong identity and an eight-slot bound. They use a uniquely named disposable test database and remove only that database. Slot-cap tests intentionally use schema-valid synthetic ciphertext; ciphertext authentication is tested separately. The checks are manual acceptance, not a headless-browser CI job. Password fields cleared; observed console errors were empty; 1280px and 390px layouts had no horizontal overflow. Five-minute timer, hidden/page-exit behavior, every UI action and real phones are not comprehensively qualified.

Brave on macOS completed the earlier console's real Blob recovery download using keyboard activation of the Save link. The actual saved file was reselected in that console and exact encrypted recovery verification succeeded. It concerned an already acknowledged test operation, so it does not newly prove the initial acknowledgment transition. No download code correction was needed. The in-app browser's download capture still timed out for the new vault export; a complete **new browser-vault download–reselect** roundtrip remains unverified. Do not generalize the Brave result to all target browsers or phones.

All nine earlier validation manifests are historical. Root app/reference tests are inherited from PR #20's green CI and rerun by PR CI; they were not newly executed locally for this isolated slice. C2 local harness is complete; C1/C3 partial; independent C4 review is unassigned; C5 browser proof execution, wallet identity/public routes and device work remain; C6 hosting is unimplemented. No deployment, migration, native-NFT wrapper, MetaMask Snap or production custody claim.
