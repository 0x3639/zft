The original package was prepared against merged PR34, `6c9d0d007445603ffe9f664351697e64d0fafc5b`; its [validation record](../research/shielded-host-validation.json) is historical and unchanged. The [configuration-pinning record](../research/shielded-host-pins-validation.json) preserves the PR36 repair. The [historical host-origin validation record](../research/shielded-host-origin-validation.json) covers the app/RPC separation against merged PR36, `c44352f14cdd09382803300195e70be6074255b5`.

This changes presentation and deployment selection, not the protocol, circuits, contracts, controller, wallet, proof worker, recovery encoding or saved-file acknowledgement. All note secrets and passwords remain client-side. An injected real wallet is required for fees and public creation authorization; the host has no fee wallet, funding/mining shim, sponsor or signing service.

## Proposed hosting boundary

The prepared [Worker configuration](../research/shielded-host/wrangler.jsonc) proposes a separate Worker named `zft-shielded-devnet-test`, with only an ASSETS binding, at **`devnet.zft.foo/shielded*`**, in the **`zft.foo`** zone. Workers.dev and preview URLs are disabled. The [Worker](../research/shielded-host/worker.mjs) accepts GET/HEAD for exact app pages and listed public assets. Unknown routes, queries, encoded paths and write methods fail closed. It has no RPC proxy, request-body upload, cookie/authentication service, secret binding, database, cron, fee key or storage mutation. The external blockchain endpoint remains **`https://devnet.zenon.foo/zvm/rpc`**; no `zenon.foo` zone, DNS or hosting change is proposed. The existing `zft-devnet` custom-domain service continues to handle app paths outside `/shielded*`; existing apex art/metadata routes remain separate. The prefix covers both `/shielded/` pages and `/shielded-assets/` proof files. Cloudflare documents that a [Worker route takes precedence over a Custom Domain on the same hostname](https://developers.cloudflare.com/workers/configuration/routing/routes/).

The Worker executes before static assets, following Cloudflare's [asset-binding configuration](https://developers.cloudflare.com/workers/static-assets/binding/). It constructs a fresh ASSETS request without caller cookies, authorization, ranges or conditional headers. Missing assets fail instead of falling back to app HTML. Every response uses no-store, nosniff, no-referrer, noindex and cross-origin isolation headers. CSP permits the selected RPC, same-origin public files, verified Blob proof code and WebAssembly. Browser-delivered JavaScript and Cloudflare remain trusted for delivery; these headers do not protect against a compromised host or another compromised application on the same origin. Applications at `devnet.zft.foo` share an origin and can access origin-scoped browser storage. Platform request metadata may still be visible to the hosting provider.

A Worker dry run confirms only the ASSETS binding and a bundle of approximately 11 KiB. Read-only Cloudflare inspection confirmed an accessible active `zft.foo` zone and the existing `devnet.zft.foo` custom domain attached to `zft-devnet`. No `/shielded*` route was listed and the candidate Worker was absent. DNS inspection returned 403. These observations do not authorize changes or prove future deployment success; recheck current route state before separately approved activation. The dry run does not establish actual hosted asset behavior or publication. Worker-first requests can consume the account's Worker request allowance, as described in [Cloudflare's billing documentation](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/). No resource or route has been created.

The corrected guard rejects all 34 while accepting the original configuration. All six host tests passed for that repair. Both the complete package and UI-only check rebuilt successfully; the complete public asset inventory and dependency inventory match the prior package byte-for-byte. This packaging-only repair adds no browser, provider, device, live transaction or crash qualification. The earlier browser trial remains scoped to its recorded source and public bundle hashes.

## App-origin correction

The earlier package incorrectly used the selected blockchain RPC domain as the app-hosting domain. The user confirmed that ZFT controls its own `zft.foo` hosting and cannot manage `zenon.foo`. This correction places the prepared app at `https://devnet.zft.foo/shielded`, with `https://devnet.zenon.foo/zvm/rpc` retained only as the external blockchain endpoint. The Worker origin check, Wrangler route/zone and generated package metadata now agree; the full configuration digest and CSP RPC destination remain unchanged.

The new regression failed the merged PR36 implementation with `ERR_ASSERTION: the shielded app must be served from the ZFT devnet host`. The corrected Worker serves the ZFT origin, sends ASSETS requests to that origin, rejects the RPC host and other origins, and retains the external RPC in CSP. All seven host tests, both package builds and a Worker dry run pass. All 43 full-package public files, all 36 UI-only files and dependency inventories/notices are byte-identical to the previous package. Only origin and route fields change in the generated package reports. [Sanitized host-origin evidence](../research/shielded-host/evidence/host-origin.json) records the scope.

The earlier browser and package evidence remains historical, including its incorrect proposed host; it is not rewritten as acceptance of this correction. No new browser trial, hosted request, wallet connection, proof, transaction or device qualification occurred. Command-line read-only RPC probes with the corrected app Origin received Cloudflare HTTP 403/error 1010; this does not establish either browser CORS acceptance or an RPC outage. Actual browser access from the hosted app remains unverified. No DNS, Worker, route or other resource was changed.
